## Resend (docs, quoted)
idempotency-keys: same key+same request -> 'the same response, without actually sending the email again'; invalid_idempotent_request = 'already been used on a request that had a different payload'; concurrent_idempotent_requests = 'another request with the same idempotency key is in progress ... safe to retry this request later'; 'Idempotency keys are kept in the system for 24 hours'; keys 1-256 characters; no statement on keys of rejected originals.
api-reference/errors: both idempotency errors are 409; invalid_idempotency_key is 400.
resend-node src/interfaces.ts: ErrorResponse = { message: string; statusCode: number | null; name: RESEND_ERROR_CODE_KEY } (both names listed).
Client-side AbortSignal cancels only the HTTP exchange; no doc guarantees the provider did not process an aborted request -> treated as ambiguous.

## Supabase docs (auth-hooks)
'HTTP Hooks should complete in 5 seconds.' 'On a retry-able error, such as an error with a 429 or 503 status code, HTTP Hooks will attempt up to three retries with a back-off of two seconds.' (source above: 429/503 retried only with retry-after, immediately; network errors after 2 s; one 5 s context for all attempts).

## Caveat (explicit)
These are the supabase/auth MASTER sources. The Auth version running on the hosted TEST / Production projects is not observable
here. The design does not REQUIRE metadata.uuid: the key is derived from the whole verified body, which is byte-identical
across attempts whenever the body is marshaled once per logical event. The hook logs "metadata.uuid present / absent" (a
presence flag only), so the TEST re-proof can confirm the hosted payload shape. Retry behavior on the hosted version must also
be re-confirmed during the TEST step.
