### 8. Sequence Privilege Findings

`business_settings.id`/`services.id` use `GENERATED ALWAYS AS IDENTITY` (see §4), not a classic `nextval()`-based sequence — Postgres identity columns do not require the inserting role to hold direct privileges on their backing sequence object for normal `INSERT` to work, unlike `SERIAL`. No separate sequence-privilege gap exists for these two tables.

### 9. Default-Privilege Findings

`pg_default_acl` for the `public` schema confirms Supabase's platform-level default: any new table created by `postgres`/`supabase_admin` automatically grants full (`arwdDxtm`) table-wide privileges to `anon`/`authenticated`/`service_role`. This explains why the migration package's existing `REVOKE ALL ... ; GRANT <narrower> ...` pattern is the correct general approach (without it, every new table would over-grant) — and confirms the fix needed for `business_settings` is to add explicit column-level `GRANT`s after the existing table-wide `REVOKE`, not a different mechanism.

### 12. Full business_settings RLS Policy Map

| Policy | Command | Role | Permissive/Restrictive | USING | WITH CHECK | Application operation affected |
|---|---|---|---|---|---|---|
| Owners can manage business settings | ALL | public | PERMISSIVE | `auth.uid()=user_id` | `auth.uid()=user_id` | All operations by the row's own owner |
| Restrict business_settings insert to role=user | INSERT | authenticated | **RESTRICTIVE** | — | `role='user'` | Signup |

| Admins can view all business settings | SELECT | authenticated | PERMISSIVE | `is_admin()` | — | Admin panel |

Postgres RLS semantics for a given command: the operation is permitted only if **at least one applicable PERMISSIVE policy** passes **AND every applicable RESTRICTIVE policy** passes. For INSERT: permissive OR-group = {"Owners can manage...", "Users can insert own settings"} (both reduce to `auth.uid()=user_id`); restrictive AND-group = {role='user', plan/trial-window}. **On Production today, both restrictive policies are genuinely declared `RESTRICTIVE`, so the plan/trial condition is a real, additional, mandatory AND-ed constraint** — it is not bypassable by the broader ownership policies.
